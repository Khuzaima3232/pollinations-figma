# Pollinations for Figma

Generate and edit images with Pollinations inside Figma, paying with your own
Pollen. Fill a selected shape or frame, edit a selected image, or drop a
generated picture onto the canvas. Text generation is included too.

## Install (development)

```sh
npm install
npm run build
```

Then in Figma: **Plugins → Development → Import plugin from manifest…** and pick
`manifest.json`. The manifest points at the built files (`code.js` and
`ui.built.html`), so build before importing.

## Use

1. **Connect account** — Figma opens the Pollinations approval page with a short
   code. Approve it; nothing is pasted into Figma. The authorization is kept in
   Figma's plugin storage for this user, not in the document.
2. Pick an image model — the list comes from your account's live catalogue.
3. Type a prompt and choose:
   - **Generate image** — places the result on the canvas.
   - **Edit selection** — exports the selected node and edits it, applying the
     result back to that node.
4. **Generate text** uses a text model and places the reply as a text layer.

## How the two halves talk

Figma plug-ins run in two places, and this one keeps that split strictly:

- **`code.ts` → `code.js`** (sandbox) has no network access. It reads the
  selection with `exportAsync`, places images with `createImage`, applies fills,
  and stores the token in `figma.clientStorage`.
- **`src/ui.js` → inlined into `ui.built.html`** (iframe) does *all* HTTP. The
  sandbox has no `fetch`, so every request to Pollinations happens in the iframe
  and results travel over `postMessage`.

The manifest therefore declares both hosts under `networkAccess.allowedDomains`.
Without that the requests are blocked, which is the usual reason a Figma plug-in
"just does nothing".

Two details that came out of reading the API typings rather than assuming:

- `figma.createImage(bytes)` is the working entry point. `createImageAsync` is
  documented elsewhere as throwing "not a supported API" inside plug-in
  sandboxes.
- An `Image` is a *handle*, not a node, and its dimensions load asynchronously —
  so the placed rectangle is sized from `image.getSizeAsync()`, not from a
  synchronous property.

Error bodies are never shown to the user, because a Pollinations error body can
echo the bearer token. Each status becomes a sentence instead.

## Verification

```sh
npm test     # vitest, 16 tests
npm run build # tsc --noEmit, then compile + inline
```

The tests import the real `src/ui.js` and drive it against a stubbed DOM,
`fetch` and `localStorage`, so the assertions cover the shipping implementation:
device flow (pending, `slow_down`, declined, incomplete), the app-key
`client_id`, per-status error mapping, the no-body-in-errors guarantee, catalogue
filtering that drops video-only models, posting generated bytes for placement,
and text generation.

The tests substitute a fast timer for the polling interval; the real 5-second
floor is asserted separately so it cannot silently disappear.

## Honest gaps

- **Not run inside Figma.** The sandbox half (`code.ts`) typechecks and its logic
  is straightforward, but placing a layer requires the Figma editor. The API
  contract, which is where the risk is, is covered by the tests.
- Live billed generation and a real device-flow approval were not automated —
  those need a signed-in account and spend Pollen.
- Published to the Figma Community is not done; that needs a Figma account review.
